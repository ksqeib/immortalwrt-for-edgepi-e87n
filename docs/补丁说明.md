插入位置的前后文原样是：

```make

endef
TARGET_DEVICES += h3c_magic-nx30-pro

define Device/hiveton_h5000m      ← 在这一行之前插入
```

### 逐项说明

**`-wpad-openssl`** 抵消官方 filogic 目标默认包里的 `wpad-openssl`。先例在 master 第 2033、2051 行（GL-MT2500 的两个变体），语法可用。

**`KERNEL_LOADADDR := 0x40080000`** 是全篇唯一一个无法从源码判定、必须上机验证的值，也是唯一一处跟 EN87 而非跟官方的地方。三套候选：

| 值 | 出处 |
| --- | --- |
| `0x40080000`（已采用） | EN87 的 e87n 与 h5000m 都用它，该组合有实机验证记录 |
| `0x40000000` | 官方所有 mt7987 板（h5000m、rfb、glinet、tenda、routerich；smartrg 例外，用 `0x43200000`） |
| `0x48000000` | dhcpd 那套 uboot 的 `CONFIG_SYS_LOAD_ADDR`，也是官方 filogic 默认值 |

`sysupgrade-tar` 打包的是 FIT，`mkits.sh` 会把 `-a $(KERNEL_LOADADDR)` 写进 FIT 的 `load` 属性，uboot 引导时按该地址搬运内核，所以值必须对。**启动不了就按 `0x40000000` → `0x48000000` 顺序试。**

**不用手写 `kmod-phy-mediatek-2p5g`。** master 上 2.5G PHY 是模块（`# CONFIG_MEDIATEK_2P5GE_PHY is not set`），但 `mt7987-2p5g-phy-firmware` 的定义带条件依赖 `+LINUX_6_18:kmod-phy-mediatek-2p5g`。这个 `LINUX_6_18` 符号由 `scripts/target-metadata.pl` 按目标内核版本自动生成（`config LINUX_$v` + `select LINUX_$v if !TESTING_KERNEL`），所以在 6.18 目标上会自然为真，模块随固件包一起进来。
（对照：`v25.12.2` 是 6.12，那版 2.5G PHY 是 `=y` 编进内核，既没有这个模块也不需要它。你已选 master，按上面写即可。）

**没有 `kmod-backlight-pwm`。** 第一版不做屏幕，DTS 里也就没有背光节点，不需要这个包。等做显示时再加回来，同时补上 `pwm_backlight_pins` 引脚组。

**`luci` 必须显式写。** 官方 filogic 的 `DEFAULT_PACKAGES` 只有 `fitblk kmod-crypto-hw-safexcel wpad-openssl uboot-envtools bridger`，不含 luci。指望 `make defconfig` 自动带上会落空。

| `defconfig/` | 不需要 |

### 三处"看起来要加、实际不用加"

**不用 disable 任何 SPI 控制器。** master 的 `mt7987.dtsi` 里 `spi0`(0x11007800)、`spi1`(0x11008800)、`spi2`(0x11009800) 默认全是 `disabled`。官方 h5000m 一条 `&spi` 语句都不写，eMMC 照常工作。EN87 在 `mt7987-emmc.dtsi` 里那句 `&spi1 { status = "disabled"; }` 是冗余的——引脚确有重叠（`spi1` 用 PIN 21-24，`emmc_45` 用 PIN 14-24），但默认值已覆盖。

**不用覆盖 `cooling-levels`。** master 的 `mt7987.dtsi` 定义 `<0 128 192 255>`，热区按下标引用（`<&fan 3 3>`、`<&fan 2 2>`、`<&fan 1 1>`）。换成 EN87 的 25 档会让下标 3 从"满速 255"变成"30"，115°C 时风扇几乎不转。官方没有任何 mt7987 板覆盖过这个数组；EN87 敢写 25 档是因为它带了 `fancontrol` 守护进程直接写 `pwm1`，绕开热区。

**PCIe 要开，而且两个控制器都开。** E87N 没有无线硬件，但有两个 M.2 NVMe 2230 槽，各接一个 PCIe 控制器。master 的 `mt7987.dtsi` 里 pcie0/pcie1 默认都是 `disabled`，要显式置 `okay`：

```dts
&pcie0 {
	pinctrl-names = "default";
	pinctrl-0 = <&pcie0_pins>;
	status = "okay";
};

&pcie1 {
	pinctrl-names = "default";
	pinctrl-0 = <&pcie1_pins>;
	status = "okay";
};
```

不加 `reset-gpios`：板载唯一的按键是系统复位键，不是给 SSD 用的。厂家 uboot 树只开 `pcie0`（引导程序用不到第二个槽），不是硬件限制。

**内存必须改成 1 GiB。** 官方 `mt7987a.dtsi` 自带的 `memory{}` 没有 `device_type`，内核扫描会忽略它，所以要自己加一个带 `device_type` 的节点：

```dts
memory@40000000 {
	device_type = "memory";
	reg = <0 0x40000000 0 0x40000000>;
};
```

## 上机验证与排查

### 刷机前：备份原厂固件

E87N 的分区表在 eMMC 上，由厂商 uboot/烧录工具创建，**不在我们的镜像里**。我们的 sysupgrade 只往名为 `kernel` 和 `rootfs` 的两个分区写数据，不动分区表。但备份原厂内核和 rootfs 仍然值得做，因为这些内容一旦被覆盖就找不回来了。

在路由器上（先用 initramfs 启动，不动 eMMC）：

```sh
# 看分区表与标签
cat /proc/partitions
for d in /sys/block/mmcblk0/mmcblk0p*; do
  echo "$(basename $d): $(grep PARTNAME $d/uevent)"
done

# 备份原厂 kernel 与 rootfs（大小按上面看到的分区容量调整）
dd if=/dev/mmcblk0p<kernel号> of=/tmp/vendor-kernel.bin bs=1M
dd if=/dev/mmcblk0p<rootfs号> of=/tmp/vendor-rootfs.bin bs=1M

# 分区表本身也在 eMMC 的 GPT 区（LBA 0-33）
dd if=/dev/mmcblk0 of=/tmp/vendor-gpt.bin bs=512 count=34
```

把这些文件拷到电脑上保存。回滚时把 kernel/rootfs 原样 dd 回对应分区即可。

### 首次启动（不刷机）

用 TFTP 加载 initramfs，串口 115200：

1. **串口无任何输出** → 改 `KERNEL_LOADADDR` 为 `0x40000000` 重编，再不行试 `0x48000000`
2. **有内核输出但挂在 rootfs** → 正常，initramfs 不需要 rootfs 分区
3. `ip link` 看 eth0/eth1 → 某个口没起来，检查 PHY 地址（E87N 外接 RTL8221B 是 **3**，h5000m 是 1）
4. `ethtool eth0` 看是否协商到 2500
5. `lsblk` 看 `mmcblk0` 与分区标签
6. `cat /sys/class/thermal/thermal_zone*/temp` 看温度，`ls /sys/class/hwmon/` 看风扇是否注册
7. **NVMe**：`lspci` 看两个控制器下是否各有设备，`lsblk` 看是否出现 `/dev/nvme0n1`、`/dev/nvme1n1`，`lsmod | grep nvme`
8. **USB**：插个 U 盘，`dmesg | tail` 看是否枚举，`lsusb`
9. **内存**：`free -h` 应显示约 1.0 GiB，若只有 256 MB 说明 `memory@40000000` 没生效
10. **DTS 编译**：`make` 第一次会真正编译设备树，本机没做过这一步，报错按行号修

都正常后再编 sysupgrade 刷机。

### 复位键

`rc.button/reset` 的行为是：短按重启，长按进 failsafe。E87N 的复位键在 `&pio 1`，与 h5000m 一致，DTS 里已定义，board.d 不需要额外配置。

## 构建机工作流（2026-10-07 实测）

构建机：Debian 13，16 核，7.7 GiB 内存，`/` 120 GiB 可用。

### 网络前提

| 目标 | 直连 | 经代理 `192.168.31.103:7890` |
| --- | --- | --- |
| `github.com` | 不通 | 200，约 1.3 s |
| `sources.openwrt.org` | 200，约 74 KB/s | 200，约 29 KB/s |
| `mirror2.immortalwrt.org` | 302 跳 sourceforge | 302 跳 sourceforge |

**结论：代理必须全局导出。** `github` 只有走代理才通；而源码镜像 `mirror2` 会 302 跳到 `sourceforge.net`，直连该站极慢，日志里出现 105 次 `curl: (28) Connection timed out` 就是它造成的。

### 踩过的坑

**坑 1：下载与编译混在一起跑。** 直接 `make -j8 V=s`，下载失败会让整个 `world` 中止：

```
make[3]: *** [Makefile:138: .../dl/elfutils-0.196.tar.bz2] Error 2
make[2]: *** [tools/Makefile:243: tools/elfutils/compile] Error 1
make: *** [include/toplevel.mk:268: world] Error 2
```

正解是文档里的做法，把下载单独拿出来先跑完：

```sh
make download -j16
make download -j1 -V=s   # 补漏，逐条看哪个还没下来
make -j16 V=s            # 下载齐了再编译
```

**坑 2：只用 `git` 的代理。** 先前只给 `git clone` 挂了 `https_proxy`，`make` 里的 `curl` 全走直连，于是卡在 sourceforge。

**坑 3：`dtc` 直接编译 DTS 报 `syntax error`。** `dtc` 不跑 C 预处理器，`#include` 必须先过 `cpp`：

```sh
cpp -nostdinc -I <内核源码>/include -I target/linux/mediatek/dts \
    -undef -x assembler-with-cpp target/linux/mediatek/dts/mt7987a-edgepi-e87n.dts /tmp/pre.dts
dtc -I dts -O dtb -o /tmp/test.dtb /tmp/pre.dts
```

### 坑 4：llvm-bpf sources 编译 OOM（2026-10-07）

第二次完整构建死在 `tools/llvm-bpf`：

```
g++: fatal error: Killed signal terminated program cc1plus
make[3]: *** [Makefile:73: .../build_dir/host/llvm-project-22.1.3.src/.built] Error 1
make[2]: *** [tools/Makefile:243: tools/llvm-bpf/compile] Error 1
```

`cc1plus` 被内核 OOM killer 杀。机器 15 GiB 内存、无 swap，`make -j16` 下 LLVM 的巨型 C++ 模板同时展开，内存不够。这段编译跑了 9261 秒（约 2.5 小时）。

**根因不是内存，是配置。** `toolchain/Config.in` 里：

```
choice BPF_TOOLCHAIN
        default BPF_TOOLCHAIN_PREBUILT if HAS_PREBUILT_LLVM_TOOLCHAIN
        default BPF_TOOLCHAIN_BUILD_LLVM
...
config HAS_PREBUILT_LLVM_TOOLCHAIN
        def_bool $(shell, [ -f llvm-bpf/.llvm-version ] && echo y || echo n)
```

树顶没有 `llvm-bpf/.llvm-version`，所以 choice 落到 `BUILD_LLVM`，从源码编 LLVM。

**为什么不能直接关掉。** `bridger` 在 filogic 的 `DEFAULT_PACKAGES` 里，它的 `DEPENDS` 带 `$(BPF_DEPENDS)`，即 `@HAS_BPF_TOOLCHAIN +@NEED_BPF_TOOLCHAIN`，会 select `NEED_BPF_TOOLCHAIN`。关掉 BPF 工具链就得不到 bridger，而 eBPF 卸载正是官方替代厂商 HNAT 的方案。

**正解：用官方预编译包。** 版本要和 `tools/llvm-bpf/Makefile` 里的 `PKG_VERSION` 对上（本例 22.1.3）：

```sh
VER=22.1.3
TAR=llvm-bpf-${VER}.Linux-x86_64.tar.zst
curl -O https://downloads.immortalwrt.org/snapshots/targets/mediatek/filogic/$TAR
```

`llvm-bpf/.llvm-version` 一出现，choice 立刻改选 `BPF_TOOLCHAIN_PREBUILT`，那 2.5 小时的 LLVM 编译整段消失。用 `fix-llvm.sh` 可一次完成。

首次刷入并启动成功。设备端诊断输出存档在 `diag.txt`。

### 已实测通过

| 项目 | 证据 |
| --- | --- |
| 内存 1 GiB | `Memory: 1006732K/1048576K available` |
| eMMC 安装 | `/overlay` 为 f2fs 挂 `/dev/loop0`（7.23 GiB），说明跑的是 eMMC 完整安装，非 initramfs |
| 分区名 | `kernel`=mmcblk0p4、`rootfs`=mmcblk0p5，与 `CI_KERNPART`/`CI_ROOTPART` 吻合 |
| MAC 各自独立 | eth0 `3a:0f:3a:cc:9e:0f`、eth1 `…9e:10`，来自 eMMC CID，两个口不同 |
| 外接 2.5G PHY | `mdio-bus:03 driver [RTL8221B-VB-CG]`，地址 3 正确（与厂商 u-boot DTS 一致） |

| 温度 | `cpu_thermal 56°C`、`mdio_bus:03 52°C` |
| 按键 | 只有 reset（`&pio 1`）。DTS 里曾按 EN87 第三方树写了 wps @ pio 0，
| | 经实机确认该按键不存在，已删除（依据厂商 uboot 提交 `be8c37611`） |
| board.json | lan=eth0 static、wan=eth1 dhcp、label_mac=wan |

### 待解决

**PCIe 双控制器均 `-110`**，LTSSM 停在 `detect.quiet`：

```
mtk-pcie-gen3 11280000.pcie: PCIe link down, current LTSSM state: detect.quiet (0x1)
mtk-pcie-gen3 11280000.pcie: probe with driver mtk-pcie-gen3 failed with error -110
mtk-pcie-gen3 11290000.pcie: PCIe link down, current LTSSM state: detect.quiet (0x0)
mtk-pcie-gen3 11290000.pcie: probe with driver mtk-pcie-gen3 failed with error -110
```

`-110` = `ETIMEDOUT`，`detect.quiet` 意味着链路对端无任何应答，**空槽就是这个表现**。需要先确认槽里是否插了盘。

若插盘后仍然 `-110`，再考虑补 `reset-gpios`。官方各板的写法不一：

| 板 | pcie0 reset-gpios |
| --- | --- |
| bpi-r4-lite、gl-be10000、rfb、tenda-be12-pro | 无 |
| hiveton-h5000m（同厂姊妹板） | `<&pio 36 GPIO_ACTIVE_HIGH>` |
| glinet-gl-mt3600be | `<&pio 38 GPIO_ACTIVE_HIGH>` |
| routerich-be7200 | `<&pio 35 GPIO_ACTIVE_LOW>` |

注意官方**没有任何 mt7987 板同时开两个控制器**：`bpi-r4-lite` 把 pcie1 设为 `disabled`。我们两个都开，属于无先例部分，且厂商 u-boot 也只开 pcie0。

**USB 缺 5V 供电**（已修）：

```
xhci-mtk 11200000.usb: supply vbus not found, using dummy regulator
```

我们只写了 `vusb33-supply`（3.3V，给 PHY），漏了 `vbus-supply`（5V，给口）。按姊妹板 h5000m 补上 `reg_usb_5v` 无 GPIO 的常开稳压器。

**按键在 userspace 的可见性未验证**：`/proc/bus/input/devices` 输出为空，但 `/proc/interrupts` 里两个 gpio-keys 中断都在。需用 `/sys/class/input` 或直接按一下看 `/dev/input/event*` 有无事件。

### 诊断脚本

`diag-on-device.sh` 只用 `/sys`、`/proc` 和 busybox，不依赖设备上没有的 `ethtool`/`lsblk`/`lspci`/`lsusb`/`evtest`。

## 已推翻的判断（2026-10-07）

**WPS 按键不存在。** 早先根据 `/proc/interrupts` 里 `mt-eint` 0 和 1 各有一个
`gpio-keys` 中断，断定 pio 0 的 WPS 键存在——这个推断是错的：内核只要 DTS 里
声明了按键就会注册中断，与物理上有没有该键无关。实机确认只有 reset 一个键。

依据是厂商 uboot 项目的提交：

```
be8c37611 mediatek: remove no existing wps button node from dts for airpi e87n
          删除的正是 gpios = <&pio 0>; 的 KEY_WPS_BUTTON 节点
```

同时删掉了 EN87 第三方树带来的这个节点。EN87 的 e87n DTS 至今仍保留它。

**第三个 LED 不是 GPIO 灯。** 所有来源（厂商 uboot、EN87、istoreos）都只定义两个
GPIO LED（pio 3 / pio 4）。第三个是网口 PHY 指示灯，由硬件直接驱动：

| 位置 | 定义 |
| --- | --- |
| 内置 2.5G PHY | `pinctrl-0 = <&i2p5gbe_led0_pins>`，function `led`、group `2p5gbe_led0` |
| 外接 RTL8221B | `realtek,led-link-select`（istoreos 用 `<0xa7 0xa7 0x00>`，我们暂未加） |

它们不注册到 `/sys/class/leds/`，所以在用户空间看不到。

**PWM 灯与本板无关。** 厂商 board common 里定义了 `pwm_led` 和 `pwm_rgb` 两个节点，
但都是 `status = "disabled"`，且它们走 `pwm0` / `pwm2`，而风扇占用的是 `pwm1`。

## LED 与按键的最终定义（2026-10-07 实机校正）

板上共三个灯。实机观察确定：

| 灯 | 状态 | 归属 |
| --- | --- | --- |
| 第 1 个 | 上电即常亮，与网线无关 | **没有任何 DTS 声明它**，充当硬件电源指示 |
| 第 2 个 | 受控 | pio 4，绿色 |
| 第 3 个 | 受控 | pio 3，琥珀色 |

三份独立来源（厂商 u-boot、EN87、istoreos）都只声明 pio 3 与 pio 4 两个可控
LED，与实机吻合。因此不定义 `LED_FUNCTION_POWER`——电源指示已由第 1 个灯硬件
承担，软件再定义一个 POWER 是重复的。

最终定义：

| 引脚 | 颜色 | function | 注册名 | 角色 |
| --- | --- | --- | --- | --- |
| pio 4 | 绿 | `LED_FUNCTION_STATUS` | `green:status` | 系统灯，承载 boot/running/failsafe/upgrade 别名 |
| pio 3 | 琥珀 | `LED_FUNCTION_WAN` | `amber:wan` | WAN 指示 |

按键只有 reset（`&pio 1`）。WPS 键不存在，依据厂商 u-boot 提交 `be8c37611`。

### 仍未确认

第 1 个灯究竟是硬接电源，还是某个默认拉高但无人声明的引脚（**pio 0 是最可疑的
候选**：它现在空闲，而官方每一块 mt7987 板都在 pio 0 放按键，厂商 u-boot 却把
那个节点删了）。若实测证明它是 pio 0，可以把它声明成真正的可控灯。

判定方法见 `diag-on-device.sh`：`ls /sys/class/leds/` 看内核注册了几个灯，
`cat /sys/kernel/debug/gpio` 看 pio 0 的占用与电平，再 export pio 0 试驱动。

### PHY 灯在本平台不可用

`mt7987.dtsi` / 官方板在 PHY 节点下写的 `leds` 子节点，在 filogic 平台上注册不出来，
因为 `CONFIG_LED_TRIGGER_PHY` 未开启（`generic/config-6.18:3485` 是 `# ... is not set`），
而 ipq40xx / mvebu / ramips / siflower 四个目标都开着。同 SoC 的 rainier 板在
`01_leds` 里引用的 `mdio-bus:0X:color:name` 同样落空。若要启用需在
`target/linux/mediatek/filogic/config-6.18` 里加 `CONFIG_LED_TRIGGER_PHY=y`。

## 第三个灯：穷举实测结论（2026-10-07）

对 `pio 0`–`pio 49` 共 50 个引脚逐个 export、设为输出、拉高 1 秒、拉低 1 秒，
**第三个灯完全无反应**。结论：该灯**硬连电源**，不受 GPIO 控制。

同时 `pio 0` 读回恒为低，说明它**悬空**，不是按键。这印证了厂商 u-boot 提交
`be8c37611` 删掉 WPS 节点的做法是对的。

因此本移植的 LED 与按键定义就此定稿：

| 引脚 | 角色 | 说明 |
| --- | --- | --- |
| （无） | 电源灯 | **硬连电源**，不经 GPIO。故不定义 `LED_FUNCTION_POWER` |
| `pio 3` | 琥珀，`amber:wan` | 由 `01_leds` 绑到 `eth1` 的 `link tx rx` |
| `pio 4` | 绿，`green:status` | 系统灯，承载 boot/running/failsafe/upgrade 别名 |
| `pio 1` | 按键 `reset` | 唯一按键 |
| `pio 0` | **空闲** | 悬空。日后可作自定义按键或灯 |
| `pio 41` | PHY IRQ | RTL8221B 中断 |
| `pio 42` | PHY reset | RTL8221B 复位 |
| `pio 36` | PCIe PERST# | 与官方 h5000m 一致 |
| `pio 7` | 风扇 PWM | `pwm 1` |
| `pio 10` / `pio 11` | 屏幕 | NV3007 的 reset / dc |

### 给日后做 GPIO 探测的提醒

上面那次穷举扫到了几个**不该碰**的引脚，应避开：

- `pio 1` —— reset 按键，拉低会触发复位
- `pio 36` —— PCIe PERST#，乱动会影响 NVMe 链路
- `pio 7` —— 风扇 PWM，拉低会让风扇停转
- `pio 10` / `pio 11` —— 屏幕 reset / dc
- `pio 41` / `pio 42` —— RTL8221B 中断与复位
- `pio 3` / `pio 4` —— 两个受控 LED

安全的探测范围是 `pio 0`、`pio 2` 以及 12 之后的空闲段，但**先查 `/sys/kernel/debug/gpio`
确认哪些已被占用**再动手。
