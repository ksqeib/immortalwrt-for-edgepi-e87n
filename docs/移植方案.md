## 一、结论先行

### 好消息：官方树对 MT7987 的支持很完整，而且有一台几乎就是 E87N 的机器

官方树里已经有 `mt7987a-hiveton-h5000m.dts`。EN87 的 E87N 设备树**本来就是从这台改的**（EN87 的 DTS 注释里写明 "Derived from the hiveton,h5000m board base"）。所以移植不是从零写，是拿官方的 h5000m 再改一遍。

硬件逐项对照：

| 项目 | 官方 h5000m | E87N | 差异 |
| --- | --- | --- | --- |
| SoC | MT7987A | MT7987A | 相同 |
| eMMC 启动 | 是 | 是 | 相同 |
| reset 键 | `&pio 1` | `&pio 1` | 相同 |
| 两个 LED | `&pio 3` / `&pio 4` | `&pio 3` / `&pio 4` | 相同 |
| 风扇 PWM | `&pwm 1` 50000ns | `&pwm 1` 50000ns | 相同 |
| 外接 2.5G PHY | RTL8221B `phy0` @1 | RTL8221B `phy1` @**3** | **地址不同** |
| 内置 2.5G PHY | `phy1` @15 | `phy15` @15 | **标签名不同** |
| 内存 | 256 MB | 256 MB | 相同 |
| rootfs | `PARTLABEL=rootfs` | `PARTLABEL=rootfs` | 相同 |
| 升级方式 | sysupgrade-tar | sysupgrade-tar | 相同 |

### 一个必须处理的冲突：HNAT

你选了「官方树」+「保留硬件加速」。**厂商 HNAT 在官方树里不存在**，这点我反复确认过：

- 官方没有 `package/mtk` 目录
- 没有 `kmod-mediatek_hnat`、`kmod-mtk_wed`、`kmod-mtk_pci`、`luci-app-turboacc-mtk`
- 内核配置里没有 `CONFIG_NET_MEDIATEK_HNAT`
- `mt7987.dtsi` 里没有 `hnat` 节点，eth 节点里也没有 `mtketh-wan` 这类属性
- master 和 v25.12.2 两个版本的补丁里搜 "hnat" 都是 **0 个**

**但是**——我查到官方树走的是另一条加速路径，而且**同样能落到硬件**：

官方 `750-net-ethernet-mtk_eth_soc-add-mt7987-support.patch` 里定义了：

```c
static const struct mtk_soc_data mt7987_data = {
	...
	.offload_version = 2,     // ← 硬件流卸载版本 2
	.ppe_num = 2,             // ← 2 个 PPE 引擎
	.has_accounting = true,
	...
};
```

配合官方已有的：

- `CONFIG_NET_MEDIATEK_SOC_WED=y`（已开；WED 本身是给无线卸载用的，E87N 无无线用不到，留着无害）
- `kmod-nft-offload` 提供 `nf_flow_table_inet` + `nft_flow_offload`
- firewall4 默认 `flow_offloading=1` + `flow_offloading_hw=1`
- `bridger` 已在 filogic 默认包里（桥接零拷贝转发）

**所以硬件加速是有的，只是实现方式从"厂商 HNAT 驱动"换成了"内核 PPE + nftables flowtable 硬件卸载"。** 我建议第一版就用这条路，它全程走 mainline 代码，内核 6.18 原生支持。

性能上与厂商 HNAT 是否等同，需要上机实测。如果实测不够用，再考虑回 EN87 树。

## 二、要改的文件（4 处改动 + 1 处确认无需改）

> **已经有现成补丁，且已整合成一条命令。** 见仓库根的 `apply.sh`：
> 它打主补丁 `patch/e87n-openwrt.patch`（8 个文件、490 处插入、0 行删除，
> 实测正反向应用均通过）、装内核补丁 `patch/999-nv3007-fbtft.patch`、
> 拷屏幕包 `package/e87n-screen/`。
> 在官方树里 `git apply port/e87n-openwrt.patch` 即可，下面的说明用于理解改动内容。

### 1. 新建 `target/linux/mediatek/dts/mt7987a-edgepi-e87n.dts`

以官方 `mt7987a-hiveton-h5000m.dts` 为底稿，做这些改动：

**必须改：**

- `model` / `compatible`：
  ```
  model = "EdgePi E87N";
  compatible = "edgepi,e87n", "mediatek,mt7987a", "mediatek,mt7987";
  ```
- **PHY 地址修正。** 官方 h5000m 的外接 RTL8221B 在 `phy0: phy@1`，E87N 的在 MDIO 地址 3。要新增节点而不是改名：
  ```dts
  &mdio {
      phy0: phy@3 {
          compatible = "ethernet-phy-ieee802.3-c45";
          reg = <3>;
          reset-gpios = <&pio 42 GPIO_ACTIVE_LOW>;
          reset-assert-us = <100000>;
          reset-deassert-us = <100000>;
          interrupt-parent = <&pio>;
          interrupts = <41 IRQ_TYPE_LEVEL_LOW>;
          realtek,aldps-enable;
      };
      phy1: phy@15 {           /* 内置 2.5G，官方同名同址 */
          compatible = "ethernet-phy-ieee802.3-c45";
          reg = <15>;
          pinctrl-names = "i2p5gbe-led";
          pinctrl-0 = <&i2p5gbe_led0_pins>;
      };
  };
  ```
  注意 `&gmac0` 的 `phy-handle` 要指向 `&phy0`（外接），`&gmac1` 指向 `&phy1`（内置）。

- **`&uart0` 必须显式开启。** 官方 `mt7987a.dtsi` 是空的，不像 EN87 在芯片级就开了：
  ```dts
  &uart0 {
      pinctrl-names = "default";
      pinctrl-0 = <&uart0_pins>;
      status = "okay";
  };
  ```
- **`&pwm` 必须显式开启**（风扇和背光都依赖）：
  ```dts
  &pwm {
      status = "okay";
      pinctrl-names = "default";
      pinctrl-0 = <&pwm_fan_pins>;
  };
  ```
- **自己定义 `pwm_fan_pins`**（官方 mt7987.dtsi 里没有，h5000m 也是自己定义的）：
  ```dts
  &pio {
      pwm_fan_pins: pwm-fan-pins {
          mux {
              function = "pwm";
              groups = "pwm1_0";
          };
      };
  };
  ```
  官方 pinctrl 驱动（patch 360）支持 `pwm1_0` 分组。
- **`aliases` 和 `stdout-path`**：E87N 原 DTS 没有，官方 h5000m 有。建议补上，串口调试要用：
  ```dts
  aliases { serial0 = &uart0; };
  chosen {
      bootargs = "console=ttyS0,115200n1 root=PARTLABEL=rootfs rootwait rootfstype=squashfs,f2fs";
      stdout-path = "serial0:115200n8";
  };
  ```

**可以照抄 EN87 的：**

- 风扇节点（`pwm-fan`，`pwms = <&pwm 1 50000 0>`，`status = "okay"`）—— **与官方 h5000m 完全一致，不产生任何差异**
- `reg_3p3v` 稳压器（官方 `mt7987.dtsi` 里没有，必须自己定义，h5000m 就是这么做的）
- eMMC 段（官方没有 `mt7987-emmc.dtsi`，要内联进 E87N 的 DTS，照抄 h5000m 的 `&mmc0` 写法，注意 `eeprom@0` 大小改为 `0x1000`）
- LED 段。E87N 用的是新版绑定（`color` + `function`，无 `label`），与 h5000m 的 `led-3`/`led-4` 不同。
  板上共三个灯：第一个上电即常亮、与网线无关，**任何 DTS 来源都未声明它**（厂商 u-boot、EN87、
  istoreos 三处都只定义 pio 3 与 pio 4），充当硬件电源指示；另外两个才是可控灯。
  实机校正后的定义（**与 EN87 不同**，EN87 把 pio 3 叫 wifi、pio 4 叫 sys）：
  ```dts
  led_sys: led-sys { gpios = <&pio 4 GPIO_ACTIVE_LOW>; color = <LED_COLOR_ID_GREEN>; function = LED_FUNCTION_STATUS; };
  led-wan          { gpios = <&pio 3 GPIO_ACTIVE_LOW>; color = <LED_COLOR_ID_AMBER>; function = LED_FUNCTION_WAN; };
  ```
  对应 sysfs 名是 `green:status` 和 `amber:wan`。
  不定义 `LED_FUNCTION_POWER`：电源指示已由第一个灯硬件承担，软件再定义一份是重复。
  `led_sys` 承载 `led-boot`/`led-running`/`led-failsafe`/`led-upgrade` 四个别名。

**不需要登记的：** 新 DTS 文件放进 `target/linux/mediatek/dts/` 后，由 `DEVICE_DTS` 机制自动编译（`include/image.mk` 里的 `Device/Build/dtb`），官方没有任何 DTS 清单文件要改。

**要加的（E87N 独有，官方 h5000m 没有）：**

- `memory@40000000` 节点，1 GiB DDR4。官方 `mt7987a.dtsi` 自带的 `memory{}` 没有 `device_type`，内核内存扫描会忽略它，所以这个节点才是生效的那个。官方所有 1 GiB 的 mt7987 板（glinet-gl-be10000、routerich-be7200、smartrg-mt-rainier）都是这个写法。
  ```dts
  memory@40000000 {
      device_type = "memory";
      reg = <0 0x40000000 0 0x40000000>;
  };
  ```
- `&pcie0` 和 `&pcie1`，两个控制器各带一个 M.2 NVMe 2230 槽，都置 `okay`。不加 `reset-gpios`——板载唯一的按键是系统复位键（接 SoC，用于恢复出厂和进 uboot 菜单），不是给 SSD 用的。
  ```dts
  &pcie0 { pinctrl-names = "default"; pinctrl-0 = <&pcie0_pins>; status = "okay"; };
  &pcie1 { pinctrl-names = "default"; pinctrl-0 = <&pcie1_pins>; status = "okay"; };
  ```
  注意厂家的 uboot 树（`bl-mt798x-dhcpd`）只开 `pcie0`，那是引导程序用不到第二个槽，不是硬件限制。

**要去掉的：**

- `&hnat` 整段（官方无此节点）
- `ext-devices-prefix` 等 HNAT 属性
- EN87 芯片级 `mt7987a.dtsi` 里的 `wifi-reset-gpios = <&pio 38>`，那是给不存在的无线模块留的

### 2. `target/linux/mediatek/image/filogic.mk`

新增设备块，放在 h5000m 附近：

```make
define Device/edgepi_e87n
  DEVICE_VENDOR := EdgePi
  DEVICE_MODEL := E87N
  DEVICE_DTS := mt7987a-edgepi-e87n
  DEVICE_DTS_DIR := ../dts
  BOARD_NAME := edgepi,e87n
  KERNEL_LOADADDR := 0x40080000
  DEVICE_PACKAGES := \
	-wpad-openssl \
	mt7987-2p5g-phy-firmware \
	kmod-hwmon-pwmfan kmod-usb3 \
	kmod-gpio-button-hotplug kmod-leds-gpio \
	kmod-crypto-hw-safexcel \
	kmod-nvme \
	f2fsck mkf2fs \
	luci luci-mod-network luci-mod-status luci-ssl-openssl
  SUPPORTED_DEVICES += edgepi,e87n EdgePi E87N
  IMAGE/sysupgrade.bin := sysupgrade-tar | append-metadata
endef
TARGET_DEVICES += edgepi_e87n
```

三处要注意：

- **`-wpad-openssl` 是必需的**，因为官方 filogic 的 `DEFAULT_PACKAGES` 带了 `wpad-openssl`，而 E87N 没有无线硬件，必须减掉它。官方有现成先例（GL-MT2500 两种变体都这么写），机制可用。
- **`luci` 必须显式写**。官方 filogic 的 `DEFAULT_PACKAGES` 只有 `fitblk kmod-crypto-hw-safexcel wpad-openssl uboot-envtools bridger`，不含 luci。指望 `make defconfig` 自动带上会落空。
- **`KERNEL_LOADADDR` 用 `0x40080000`**。这是唯一一处跟 EN87 而非跟官方的地方，也是全篇唯一一个我无法从源码判定、只能上机验证的值。三套候选的出处：

  | 值 | 出处 |
  | --- | --- |
  | `0x40080000`（已采用） | EN87 的 e87n 与 h5000m 都用它，且该组合有实机验证记录 |
  | `0x40000000` | 官方所有 mt7987 板（h5000m、rfb、glinet、tenda、routerich） |
  | `0x48000000` | dhcpd 那套 uboot 的 `CONFIG_SYS_LOAD_ADDR`，也是官方 filogic 的默认值 |

  为什么这个值较真：`sysupgrade-tar` 打包的是 FIT 镜像，`mkits.sh` 会把 `-a $(KERNEL_LOADADDR)` 写进 FIT 的 `load` 属性，uboot 引导 FIT 时会按这个地址搬运内核。地址不对就卡在 uboot、串口无内核输出。

  **启动不了就按 `0x40000000` → `0x48000000` 的顺序试。**

**基线定为 master（6.18），下面说明 2.5G PHY 为什么不用手写依赖。**

master 上 2.5G PHY 是模块（`# CONFIG_MEDIATEK_2P5GE_PHY is not set`），但是 `mt7987-2p5g-phy-firmware` 的定义里带了条件依赖：

```make
Package/mt7987-2p5g-phy-firmware = $(call Package/firmware-default,MT7987 built-in 2.5G Ethernet PHY firmware,@TARGET_mediatek_filogic +LINUX_6_18:kmod-phy-mediatek-2p5g,LICENCE.mediatek,,nonshared)
```

`LINUX_6_18` 这个符号由 `scripts/target-metadata.pl` 按目标内核版本自动生成（`config LINUX_$v`，配合 `select LINUX_$v if !TESTING_KERNEL`），所以在 6.18 目标上恒为真，`kmod-phy-mediatek-2p5g` 会随固件包一起被拉进来。因此 `DEVICE_PACKAGES` 里写 `mt7987-2p5g-phy-firmware` 就够，不必额外写模块名。

（对照：`v25.12.2` 是 6.12 内核，那版 `CONFIG_MEDIATEK_2P5GE_PHY=y` 直接编进内核，既没有这个模块也不需要它。基线已定 master，按上面的写法即可。）

### 3. `filogic/base-files/etc/board.d/02_network`

加两处（照抄官方 h5000m 的写法，去掉 `hnat` 网口）：

在接口映射的 case 里加：

```
	edgepi,e87n|\
	hiveton,h5000m|\
	...
		ucidef_set_interfaces_lan_wan eth0 eth1
```

在 MAC 生成的 case 里加：

```
	edgepi,e87n)
		lan_mac=$(macaddr_generate_from_mmc_cid mmcblk0)
		wan_mac=$(macaddr_add "$lan_mac" 1)
		label_mac=$wan_mac
		;;
```

**这里与 EN87 不同：** EN87 写的是 `ucidef_set_interfaces_lan_wan "eth0 hnat" eth1`，把 HNAT 虚拟口当作 LAN 成员。走官方原生卸载后 `hnat` 口不存在，所以改成官方的 `eth0 eth1` 两口模型。

### 4. `filogic/base-files/lib/upgrade/platform.sh`

加三处 `edgepi,e87n`，照抄 h5000m 现成的三个位置：

1. `platform_do_upgrade` 里共用的 `CI_KERNPART=kernel` + `CI_ROOTPART=rootfs` + `emmc_do_upgrade "$1"` 分支
2. `platform_check_image` 里的 tar magic `ustar` 校验分支
3. `platform_copy_config` 里的 `emmc_copy_config` 分支

**好消息：官方已经支持 MT7987 的 eMMC 升级了**，h5000m 就在这三个列表里，照着加一行即可。`emmc_do_upgrade` 定义在 `package/base-files/files/lib/upgrade/emmc.sh`，会自动识别 FIT 或 tar。

不需要改。官方 `config-6.18` 里 MT7987 相关符号已经齐了：

CONFIG_COMMON_CLK_MT7987_ETHSYS=y
CONFIG_PINCTRL_MT7987=y
CONFIG_NET_MEDIATEK_SOC=y
CONFIG_NET_MEDIATEK_SOC_WED=y

## 五、上机验证顺序

### 第 0 步：先备份原厂固件（在做任何事之前）

E87N 的分区表在 eMMC 上，由厂商 uboot/烧录工具创建，**不在我们的镜像里**。我们的 sysupgrade 只往名为 `kernel` 和 `rootfs` 的两个分区写数据，不动分区表。但原厂 kernel 与 rootfs 一旦被覆盖就找不回来了，值得先留一份。

先用 initramfs 启动（不碰 eMMC），然后在路由器上：

```sh
# 看分区表与 GPT 标签名
cat /proc/partitions
for d in /sys/block/mmcblk0/mmcblk0p*; do
	echo "$(basename $d): $(grep PARTNAME $d/uevent)"
done

# 备份原厂 kernel 与 rootfs（分区号按上面看到的填，大小按容量调整）
dd if=/dev/mmcblk0p<kernel号> of=/tmp/vendor-kernel.bin bs=1M
dd if=/dev/mmcblk0p<rootfs号> of=/tmp/vendor-rootfs.bin bs=1M

# 分区表本身（GPT 主副副本，LBA 0-33）
dd if=/dev/mmcblk0 of=/tmp/vendor-gpt.bin bs=512 count=34
```

把这些文件拷到电脑上保存。回滚时把 kernel/rootfs 原样 dd 回对应分区即可。

### 验证步骤

1. **先编 initramfs，不刷机**。用 TFTP 或 U 盘启动，验证串口有输出、能进系统。这一步不改动路由器上的任何东西。
2. 确认网口：`ip link` 看 eth0/eth1 是否起来，`ethtool eth0` 看 2.5G 协商。
3. 确认 eMMC：`lsblk` 看 `mmcblk0` 和分区 `PARTLABEL=rootfs`。
4. 确认温度与风扇：`cat /sys/class/thermal/thermal_zone*/temp`，`ls /sys/class/hwmon/`。
5. 都正常后再编 sysupgrade 刷机。
6. **刷机前务必确认能进 uboot/tftp 恢复**。

### 已知风险点（按可能出现顺序）

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| `KERNEL_LOADADDR` 不对 | 卡在 uboot，无内核输出 | 依次试 `0x40000000`、`0x48000000` |
| PHY 地址不是 3 | 某个网口 link 不上 | 试 1（h5000m 的值） |
| `pwm1_0` 分组冲突 | 启动日志报 pinmux 错误 | 换 `pwm1_1` |
| 内存只认到 256 MB | `free -h` 显示 256MB | 检查 `memory@40000000` 节点是否被 DTS 编译进去 |
| NVMe 认不到盘 | `lspci` 无设备 | 检查 `pcie0`/`pcie1` 是否 `okay`、`lsmod` 看 nvme |
| USB-A 口不供电 | 插 U 盘无反应，`dmesg` 无枚举 | 我的 `&ssusb` 只写了 `vusb33-supply`（与官方 routerich-be7200 同款）。若实物需要 VBUS 供电，补一个 `reg_usb_5v` 固定调节器并加 `vbus-supply = <&reg_usb_5v>`，参照 h5000m |
| eMMC 的 `eeprom@0` 大小 | MAC 读不到 | E87N 靠 `mmcblk0` CID 生成 MAC，不依赖 eeprom |
| 2.5G PHY 模块未加载 | eth1 不通 | 确认 `mt7987-2p5g-phy-firmware` 已装、`lsmod` 看 mtk-2p5ge |
| DTS 编译报错 | 构建中断 | **本机没有编译器（无 gcc/make/flex/bison），DTS 从未经过 `dtc` 真正编译过**。只做过括号配平与标签解析检查。若报 phandle 或属性错误，按报错行号修 |

### 尚未验证的事（诚实的边界）

- **DTS 未经过真正的编译器**。本机无工具链，四棵树里的 `dtc` 源码也编译不了。上机 `make` 时才会第一次真正编译。
- **`KERNEL_LOADADDR`、PHY 地址、USB VBUS** 三项只能实测确认。
- **两路 NVMe 的实际识别**需 `lspci` 验证是否真如规格所述各接一路。

## 六、已做 / 不做的事

屏幕与风扇这两项原先列为"第二版再说"，现在结论如下：

| 项目 | 状态 | 说明 |
| --- | --- | --- |
| NV3007 屏幕 | **已做** | 见 §屏幕。`patch/999-nv3007-fbtft.patch`（可加载 `fb_nv3007.ko`）+ `package/e87n-screen/`（GPIO524 背光）。已上机验证：朝向与厂商寄存器表均正确 |
| 屏幕 dashboard | **已做** | `package/e87n-display/`：自写 C 渲染器，自带 Oswald 字模（预先栅格化），直写 `/dev/fb0` 画温度大字、时钟、CPU/内存/客户端、速率曲线。非 istoreos 那个 LVGL 9.4 GUI（26 MB 源码、4 个页面），不收录 |
| 风扇服务 | **不做** | 内核 thermal 曲线已按本板调过（52/68/80 °C，见 §风扇）。原厂 `fancontrol` 是闭源二进制，且绕过 thermal zone 直接写 `pwm1` |
| 厂商 HNAT | 需要把 9752 行驱动 + 10 个补丁从 6.6 前移到 6.18，风险高，建议实测官方卸载不够用再说 |
| OpenClash | EN87 有现成的 `e87n-openclash.config` 可参考 |
| Aurora 主题 | `luci-theme-aurora`，官方 feed 里可能有 |

**没有无线这一项。** E87N 的硬件不带无线，不是"第一版先不做"——EN87 树里的 `96-e87n-mt7922-wireless`、`kmod-mt7922-firmware`、`wpad-openssl`、`wireless-regdb` 那一整套都是为不存在的硬件准备的，移植时全部不要。

## 附：本次调查推翻过的判断

为保证不误用，记录三处我一度搞错、后来纠正的结论：

1. **"mt798x-6.6 和 EN87 是两个独立项目"** —— 错。EN87 的 git 历史包含 `30fbc1d6de`（mt798x 分支 HEAD），是父子关系。这个结论是在你切到正确分支后才确认的。
2. **"官方树完全不支持 mt7987"** —— 错。官方对 MT7987 支持很完整，只是我最初搜的是 `7987` 字面量，漏看了按板名的分支（h5000m 在 `platform.sh` 里出现 3 次）。
3. **"厂商 HNAT 是唯一的硬件加速方案"** —— 错。官方 `mt7987_data` 里 `.offload_version = 2` + `.ppe_num = 2`，走内核 PPE + nft flowtable 同样能下硬件。
